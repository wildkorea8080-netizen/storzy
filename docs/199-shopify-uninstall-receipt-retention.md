# Shopify 앱 삭제 수신 원장 보존 정책

`app/uninstalled` Webhook 수신 원장은 앱 삭제 뒤 도착하는 `shop/redact` 요청을 기존 워크스페이스로 연결하기 위해 최대 7일 동안만 Shopify 스토어 도메인과 연결 식별자를 보관한다.

시간별 `privacy-sla-scan` 예약 작업은 SLA 경보 생성 후 보존 기한이 지난 원장을 자동 익명화한다. 행과 수신 시각, 워크스페이스 일치 여부는 운영 감사 통계를 위해 유지하지만 다음 식별자는 복구할 수 없는 값으로 교체하거나 제거한다.

- Webhook ID: 원장 UUID 기반 `expired:<uuid>` 값으로 교체
- Shopify 스토어 도메인: `expired.invalid`로 교체
- 연결 및 워크스페이스 ID: `NULL`로 제거

이미 `shop/redact` 처리로 `redacted.invalid`이 된 원장과 이미 만료된 원장은 다시 변경하지 않는다. 작업은 같은 행에 반복 실행해도 결과가 달라지지 않으며, 완료 결과는 `shopify-uninstall-retention.completed` 구조화 로그의 익명화 건수로 확인한다.

SLA 경보 스캔과 원장 익명화는 같은 scheduler 프로세스에서 순서대로 실행하지만 장애는 서로 격리된다. 한 단계가 실패해도 나머지 단계는 계속 실행하며, 각각 `privacy-sla.scan.failed`와 `shopify-uninstall-retention.failed`로 원인을 구분한다. 하나라도 실패하면 scheduler는 실패 종료되어 운영 경보와 재시도 대상이 된다.

관리자 개인정보 화면의 **개인정보 자동 정리** 패널은 최근 24시간 및 누적 익명화 건수, 기한이 지났지만 아직 처리되지 않은 건수, 마지막 익명화 시각을 표시한다. 예약 작업의 최근 heartbeat가 150분을 넘으면 `실행 지연`, 마지막 실행이 실패했으면 `실패`로 표시한다. 이 정보는 관리자 인증이 필요한 `GET /api/admin/privacy-maintenance/summary`에서 제공한다.

관리자 홈은 같은 보호 API를 사용해 예약 작업 실패·150분 이상 실행 지연·기한 경과 미처리 중 하나가 있을 때만 주의 배너를 표시한다. 정상 상태에서는 배너를 숨겨 일반 운영 흐름을 방해하지 않으며, 이상 상태에서는 개인정보 운영 화면으로 바로 이동할 수 있다.

외부 운영 채널 전송의 기준이 되는 `privacy_maintenance_incidents` 원장은 SLA 스캔 실패와 앱 삭제 원장 정리 실패를 요청 단위 SLA 경보와 분리해 기록한다. 동일 장애 유형은 하나의 열린 사건으로 갱신하며, 다음 실행에서 해당 단계가 정상화되면 자동으로 해결한다. 오류 메시지는 줄바꿈을 제거하고 1,000자로 제한한다.

기존 `privacy-alert-delivery` scheduler는 열린 유지관리 사건도 `PRIVACY_MAINTENANCE` 범주의 서명 Webhook으로 전송한다. 사건 ID와 최초 발생 시각의 조합으로 같은 장애 회차의 중복 알림을 막고, 해결 후 재발하여 최초 발생 시각이 바뀌면 새 알림을 생성한다. 실패한 전송은 30초부터 최대 1시간까지 지수 백오프로 재시도하며 `PRIVACY_ALERT_*` 환경 설정과 서명 비밀값을 요청 SLA 경보와 공유한다.

전송 worker가 Webhook 호출 도중 종료되면 `RUNNING` 임대가 남을 수 있다. 다음 scheduler 실행은 만료된 요청 SLA 및 유지관리 경보 임대를 `FAILED`로 회수하고 즉시 재시도 대상으로 되돌린다. 실행 중 임대의 만료 시각에는 부분 인덱스를 적용해 원장 규모가 커져도 복구 조회 범위를 제한한다.

관리자 개인정보 화면은 열린 유지관리 사건을 최근 갱신 순서로 최대 10건 표시한다. 사건 유형과 오류, 발생 시각뿐 아니라 외부 Webhook의 전송 대기·전송 중·완료·실패 상태, 시도 횟수와 마지막 전송 오류도 함께 제공하므로 DB에 직접 접근하지 않고 전달 상태를 확인할 수 있다.

실패한 유지관리 Webhook에는 관리자 화면의 **재전송** 작업을 제공한다. 담당자 ID와 1~500자의 사유를 필수로 받아 현재 열린 사건 회차의 `FAILED` 전송만 `PENDING`으로 되돌리며, 작업 전후 상태와 담당자·사유는 `privacy_maintenance_delivery_actions` 감사 원장에 기록한다. 완료·대기·전송 중 상태는 수동 재전송할 수 없다.

각 열린 사건의 **재전송 기록**에서는 최근 감사 작업을 최대 20건 확인할 수 있다. 관리자 인증이 필요한 `GET /api/admin/privacy-maintenance/incidents/:id/actions`가 담당자, 재전송 사유, 작업 전후 상태와 수행 시각을 최신순으로 반환하며 서버는 조회 한도를 1~100건으로 제한한다.

관리자가 실패 경보를 재전송하면 누적 `attempts`를 `0`으로 초기화해 새 재시도 예산을 부여한다. 이 규칙은 유지관리 경보뿐 아니라 요청 SLA 경보와 Shopify 토큰 경보에도 동일하게 적용되어, 기존 최대 시도 횟수에 도달한 경보도 실제로 worker가 다시 선택할 수 있다.

재시도 예산을 초기화하기 전의 횟수는 각 경보 감사 작업의 `before_attempts`에 보존한다. 기존 감사 행은 `NULL`을 허용하고 신규 수동 재전송부터 0 이상의 값을 기록하며, 유지관리 재전송 기록 화면에서는 `이전 시도 N회`로 표시한다.
